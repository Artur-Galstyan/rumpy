# 008 — sum

Write `sum` in `exercises/03_reductions/008_sum.rs`.

Reshape and transpose return arrays. A reduction combines many values into one result.
This lesson reduces every element to one Rust `f64`, without a result buffer.

## Public contract

```rust
pub fn sum(a: &Array) -> f64
```

Start with positive zero (`0.0_f64`). Add each value from `a.as_slice()` in flat, left-to-right order.
Each addition uses `f64` arithmetic. Do not reorder, group, compensate, or parallelize the additions.
The input shape and every input value bit stay unchanged.

All ranks are valid. Shape `[]` describes one scalar value, not an empty array.
That scalar participates in the initial addition. In particular, a scalar `-0.0` produces `+0.0`.
Any zero-length axis makes the array empty. Every empty array returns positive zero.
Shapes `[usize::MAX, 0]`, `[0, usize::MAX]`, and `[usize::MAX, usize::MAX, 0]` must finish promptly.
Do not traverse axis lengths or compute a new shape product. The existing storage already defines the element count.

Infinities follow IEEE arithmetic. Opposite infinities produce NaN. Finite overflow may produce infinity and is not an error.
A NaN input produces a NaN result. Only the result's NaN class matters, not its sign, payload, or signaling state.
The input NaN bits must still remain unchanged. Signed zeros and subnormal values follow normal `f64` addition.

## Supported API

Original API: [numpy.sum](https://numpy.org/doc/stable/reference/generated/numpy.sum.html).
The comparable NumPy call is `np.sum(a, dtype=np.float64)` with its default `axis=None`.

This Rust API accepts only the existing owned, contiguous, row-major `f64` array.
There is no `axis`, `keepdims`, `dtype`, `out`, `where`, or `initial` parameter.
Views, arbitrary strides, integer arrays, and other element types are outside this lesson.
The return value is a Rust scalar, not an `Array` or a `Result`.

**Addition order differs from NumPy's general contract.** NumPy can use partial pairwise summation.
Its result is not necessarily bit-identical to this left-to-right reduction for ill-conditioned inputs.
This lesson chooses a simple, explicit order rather than NumPy's more accurate reduction strategy.
Do not use NumPy's result as an exact oracle for arbitrary floating-point inputs.

## Examples

| Input shape | Flat values | Result |
| --- | --- | --- |
| `[2, 2]` | `[1.0, 2.0, 3.0, 4.0]` | `10.0` |
| `[3]` | `[0.5, -0.25, 0.125]` | `0.375` |
| `[]` | `[-0.0]` | `+0.0` |
| `[2, 0, 3]` | `[]` | `+0.0` |
| `[4]` | `[1e16, 1.0, -1e16, 1.0]` | `1.0` |

The last example tests addition order, not an exact real-number sum.
Floating-point addition rounds after each operation, so a different grouping can change the result.
The contract tests check these examples without a tolerance.

## Available helpers

1. Read `Array::as_slice`, `size`, and `shape` in `src/array.rs`.
2. Use a standard slice iterator or a `for` loop to visit the stored values.
3. Use a typed `f64` accumulator and ordinary addition. A sequential `fold` is also allowed.
4. Use `to_bits()` for exact non-NaN test results and input preservation. Use `is_nan()` for NaN results.
5. Preserve the tests and leave earlier exercises and library code unchanged.

No new constructor, shape helper, allocation, error type, or external crate is necessary.
Avoid an iterator reduction without an explicit initial value, which treats the first element differently.
A custom ordered loop makes the floating-point order easier to audit than a generic summation helper.
